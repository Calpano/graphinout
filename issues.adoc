= Open Issues
:toc:

Issues surfaced while triaging test-log spam on 2026-06-30 (full `mvn clean test`, all
modules). After silencing the three noise sources (GmlTokenizer per-token WARN, Apache
Jena's RIOT logger, and the `ReaderTests` probe catch), the log shrank from ~890,000 to
~15,900 lines — and the warnings below stopped being drowned. Most are emitted because
detection probes every reader against every file, but several point at genuine behaviour
worth fixing. Severity is the author's estimate; "investigate" means *confirm whether it
fires on inputs that should parse, vs. detection probing incompatible files*.

== Done (noise removed)

* `GmlTokenizer` no longer logs a WARN per unhandled token; it reports a single capped
  `ContentError` and bails once the input is clearly not GML (was ~860k log lines).
* `logback-test.xml` (base) silences `org.apache.jena` — its RIOT parser logs at ERROR on
  non-RDF input; the RDF reader already surfaces real problems as `ContentError`s.
* `ReaderTests.testWithAllResource` logs expected probe failures at DEBUG, not WARN+stacktrace.
* *log-content-errors-as-ContentError sweep (read side):* readers now report parse problems
  through the `ContentError` handler instead of logging them directly. Converted to a reported
  `ContentError`: `Json2CjWriter` unknown-property (I1) and `Graphml2CjDocument` undeclared-key
  (I2). Demoted to DEBUG (already reported elsewhere): `GraphmlReader`, `Xml2GraphmlWriter`,
  `GexfReader`, `OcifDoc2CjDoc` (ocif + ocif07), `CjNormalizer`. Added the no-Throwable
  `IHandleContentErrors.sendContentError_Warn(String)` overload. Full test log is now ~3,400
  lines (was ~890,000).

== Genuine issues

=== I1 — CJ reader drops unknown properties [HIGH / investigate — now reported]
`Json2CjWriter` encounters a key that is not a known CJ property, then drops the value.
Observed keys: `options` (134×, on RootObject — likely a grale or OCIF document property), and
JSON-LD/RDF keys `@id` `@type` `@graph` `nodes` `maker` `primaryTopic` `label` `created`, plus
`foaf:*` / full-IRI keys.

* *Status:* no longer a silent WARN — it now reports a `ContentError` (Warn) so the caller can
  see the drop. (Surfaced no asserting-test failures, i.e. it fires on probe/non-CJ paths.)
* *Risk:* still **data loss** — the value is dropped, just visibly now.
* *Action:* determine which reader+fixtures produce each key; if they are real inputs (grale
  `options`, JSON-LD `@id`/`@type`), model the property rather than dropping it.

=== [x] I2 — GraphML `<data>` referencing an undeclared `<key>` [MEDIUM — now reported + recovered]
`Graphml2CjDocument` hit `<data key='dN'>` with no matching `<key id='dN'>`.

* *Status:* now reports a `ContentError` (Warn) and recovers by auto-creating a string key (so
  no data loss). `GraphmlReaderContentErrorTest` now tolerates recoverable Warns, asserting only
  no Error-level errors.
* *Found:* the external fixture `graph-test-data/xml/graphml/yworks/yed-3.12.2/graph1_test.graphml`
  references 5 undeclared keys (`d5 d6 d7 d9 d10`), plus one more file with a single undeclared
  key — both are malformed per the GraphML spec (every `<data key>` must be declared).
* *Action:* none required (recovery is correct); optionally fix the fixtures to declare the keys.

=== I3 — Neo4j writer emits empty output for some CJ inputs [DONE]
The two inputs (`custom-data-simple2.cj.json`, `custom-data-simple3.cj.json`) have *only*
document-level `data` and no `graphs`/nodes/edges. A Neo4j property graph is nodes +
relationships, so empty output is correct — not a writer bug. But it was *silent* data loss.

* *Fix:* `Neo4jWriter` (which already extends `BaseCjOutput implements IHandleContentErrors`) now
  reports a `ContentError` from `documentEnd()` when nothing was written ("No nodes or edges to
  export to Neo4j; the document has no graph content"). `Neo4jReader.createCjStream` forwards the
  configured handler to the writer, so a CLI convert surfaces it on stderr. `Neo4jRoundTripTest`
  now asserts empty output is always explained by a reported `ContentError`, never silence.

=== I4 — GraphmlReader logged every ContentError at WARN [DONE]
`GraphmlReader` and `Xml2GraphmlWriter` both *reported* a `ContentError` and then re-logged it
at WARN. Fixed: the redundant logs are now DEBUG; the `ContentError` handler is the single
channel.

=== I5 — OCIF: many fixtures lack a schema declaration [DONE]
The warning is legitimate — OCIF files SHOULD declare a schema — so it is kept, not downgraded.

* `reader-ocif` now defaults to **v0.7.0** when no schema is given (was v0.6), via a new
  `OCIF.OcifSchema.DEFAULT` constant, matching `reader-ocif07` (already v0.7.x).
* All 42 schema-less synthetic fixtures (`ex01`–`ex20`, `hello-world` in both
  `reader-ocif*/src/test/resources/json/ocif/`) now declare an explicit `"ocif"` schema, matching
  each module's version: `reader-ocif` → `spec.canvasprotocol.org/v0.6`, `reader-ocif07` →
  `canvasprotocol.org/ocif/v0.7.1`. (Wild fixtures were not touched — there were none here.)
* `ex04`'s EXPECTED round-trip fixture updated to the now-explicit v0.6. Full build green; the
  "Found no OCIF schema" warning dropped from 84 to 0.

=== I6 — A few Jena `riot` ERROR lines still leak [DONE]
The ~6 `ERROR riot - …` lines came from `GraphinoutCliTest`: the `cli` module had no
`logback-test.xml`, so its tests fell back to `cli/src/main/resources/logback.xml` (no
suppression). Jena logs these under a *top-level* logger named `riot`, which the package-scoped
`org.apache.jena` OFF rule does not match.

* *Fix:* added `cli/src/test/resources/logback-test.xml` silencing `org.apache.jena` and `riot`,
  and added `<logger name="riot" level="OFF"/>` to base's config too. `ERROR riot` lines: 6 → 0.
* *Remaining (separate, ~1 line):* `ERROR GraphmlValidator - SAX error` from a malformed-graphml
  test — the validator logs instead of reporting via `ContentError`; small follow-up if wanted.

== Known limitations (not bugs)

* I7 — `MermaidOutput`: `Cannot represent hyper-edge in Mermaid flowchart`. Mermaid flowcharts
  have no hyper-edge syntax; this is an inherent limitation, now surfaced via the writer's
  `ContentError` channel (below) rather than logged.

== Cross-cutting note [DONE]
The root cause of the original spam was an anti-pattern: **readers/writers logging data problems
directly instead of reporting them via the `ContentError` handler.** Both sweeps are done:

* *Read side* — see the Done section.
* *Write side* — `GioWriter` gained a `default setContentErrorHandler(Consumer<ContentError>)`;
  the 5 registered output writers (`GmlOutput`/`GmlWriter`, `DDotOutput`, `CjDocument2D2`,
  `MermaidOutput`, `TgfOutput`) plus `TripleTextOutput` now report write-time data loss
  ("Cannot represent hyper-edge …", "Skip node without id") through that channel instead of
  `log.warn`. The CLI convert command wires one handler into both reader and writer, so write-time
  losses print to stderr alongside parse errors. (Without a handler set, the loss is silent — same
  contract as readers.)
